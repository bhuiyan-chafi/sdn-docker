# Lab Summary and Q&A

## Q&A

**Q: In the current configuration, `pc1` has an IP of `192.168.1.10`. The `santanna` switch has an IP of `192.168.1.1` on `br0`. However, when I ping `192.168.1.1` from `pc1`, it says "Destination host unreachable". A `tcpdump` on the switch shows the ARP request arriving, but the switch never replies. Why is that?**

**A:** This is a classic example of Software-Defined Networking (SDN) behavior, specifically how the Control Plane overrides the Data Plane.

Here is exactly what is happening:

### The Problem: ONOS Kidnapped the Brain

1. **The packet arrives:** `pc1` sends the ARP request into the wire. It arrives physically at `eth2` on the `santanna` switch.
2. **OVS intercepts it:** Because `eth2` is enslaved to `br0`, the Open vSwitch engine intercepts the packet.
3. **ONOS says "Drop it":** `br0` is currently controlled by ONOS. When ONOS connects to a switch, it wipes out the default "normal switch" behavior and replaces it with its own OpenFlow rules.
4. **The `LOCAL` port is ignored:** The IP address `192.168.1.1` actually lives on the internal Linux networking stack (which OVS calls the `LOCAL` port). ONOS applications (like `fwd` and `proxyarp`) are designed to route traffic between external hosts, not to the switch itself. ONOS does not flood ARP requests to the `LOCAL` port.

### The Result

The ARP request hits `br0`, ONOS doesn't know what to do with an ARP for `192.168.1.1`, so the packet is dropped. **The internal Linux kernel of the switch never even sees the ARP request**, which is why it never replies!

### How to prove this:

If you want to prove that your IP assignment is correct and that ONOS is the one blocking it, you can temporarily disconnect the switch from the controller by running this command inside the `santanna` switch:

```bash
ovs-vsctl del-controller br0
```

The moment you do this, OVS will enter `fail-standalone` mode and revert to acting like a traditional Linux bridge. If you run the ping from `pc1` again, **it will work instantly** because the switch is no longer asking ONOS for permission to process the ARP request. To reconnect it later, simply run `ovs-vsctl set-controller br0 tcp:131.114.54.2:6653`.

**Q: I activated the `fwd` and `proxyarp` apps in ONOS. Now, when I ping from `pc1` to `192.168.1.1` (the switch), it no longer says "Destination host unreachable" but the ping just gets stuck. A tcpdump shows the ICMP echo request arriving (`IP 192.168.1.10 > 192.168.1.1: ICMP echo request`), but there is no reply. I also dumped the OpenFlow rules and found a rule sending packets destined to the switch's MAC address out of `eth1`. Will enabling NAT and IP forwarding in the switch fix this?**

**A:** No, NAT or IP forwarding inside the switch will not fix this, because the packet never even reaches the switch's Linux IP forwarding engine!

Here is what happened:

### 1. Why ARP is working now

Because you activated `fwd` and `proxyarp`, ONOS finally knew how to handle the ARP request. It flooded the ARP, the switch's internal OS replied, and `pc1` successfully learned the switch's MAC address. That is why you no longer see "Destination Host Unreachable".

### 2. Why the Ping gets stuck

The problem lies in the OpenFlow rules generated by ONOS, specifically this one you found:
`priority=10, in_port=eth2, dl_src=..., dl_dst=9e:65...[switch MAC] actions=output:eth1`

When `pc1` sends the ICMP request, it addresses it to the switch's MAC address. The packet hits the OpenFlow engine (OVS) at Layer 2. ONOS (specifically the `fwd` app) got confused by this MAC address. Because ONOS is designed to route between external hosts, it assumes this MAC address belongs to another host on the network. So, it literally kicks the ping out of `eth1` (towards the UniPI switch) before the Linux kernel even gets a chance to look at the IP header!

### How to actually fix it

To fix this, we have to manually inject a high-priority rule into the switch to override ONOS. We need to tell the OpenFlow engine: _"If a packet is destined for your own MAC address, send it to your internal LOCAL OS, do not send it out eth1."_

Run this exact command in the `santanna` switch (replacing with your actual MAC):

```bash
ovs-ofctl add-flow br0 -O OpenFlow13 "priority=50000,dl_dst=9e:65:a0:e2:5e:46,actions=LOCAL"
```

Once added, OpenFlow will force the ping into the switch's local IP stack, the switch will generate an Echo Reply, and the ping will work!

**Q: Why is the `fwd` app unable to forward packets between different subnets (e.g. `pc1` to `pc2`)?**

**A:** The `fwd` app is a simple **Layer 2 (MAC-based) learning switch**. It is completely blind to IP routing. When `pc1` tries to reach `pc2` in a different subnet, it sends the packet to its default gateway's MAC address (e.g. `192.168.1.254`).

Even if `fwd` blindly floods this packet across the network and it arrives at `pc2`'s switch port, **`pc2` will drop it**. Why? Because the destination MAC address on the packet belongs to the virtual gateway, not to `pc2`. A true router must perform **MAC Rewriting** (changing the destination MAC to match the next hop or final destination) and TTL decrementing. The `fwd` app does not do this.

This lab proves that without a complex Layer-3 routing application (like SDN-IP or Segment Routing) handling MAC rewrite rules in the flow tables, simple reactive forwarding cannot route traffic across subnets.

**Q: If we just install manual instructions (like `actions=LOCAL`) in every switch, it will work, right?**

**A:** It depends on what you mean by "work".

If you mean _"Will the PCs be able to ping their connected switches?"_, then **Yes**. Adding the `actions=LOCAL` rule to every switch tells the switch to hand packets destined for its own MAC directly to its local Linux kernel, allowing the switch to respond to its own IP address.

But if you mean _"Will this allow PC1 to ping PC2 across subnets?"_, then **No**.
The `LOCAL` rule only tells the switch to consume the packet. For `santanna` to forward a packet from `pc1` across the network to `pc2`, you would have to enable IP forwarding inside `santanna`'s Linux kernel and write traditional `route add` commands in the OS. If you do this in every switch, you have effectively turned the switches back into old-school, distributed Linux routers, which **completely defeats the purpose of having an SDN!**

The "SDN Way" to fix routing manually without a smart app would be to write OpenFlow rules that perform MAC rewriting and TTL decrementing in the switch hardware (e.g., `actions=mod_dl_dst:<pc2_mac>,dec_ttl,output:eth1`). This perfectly illustrates why we use SDN controllers: a good routing app calculates and pushes these complex `mod_dl_dst` rules automatically, so network admins don't have to write them manually for every connection!

**Q: If I manually inject a rule (like `actions=LOCAL`) into the switch using `ovs-ofctl`, it works for a few seconds and then gets deleted. Why does it get deleted?**

**A:** It gets deleted because **ONOS is designed to be in "complete-control."**

In Software-Defined Networking, the controller is meant to be the absolute **Single Source of Truth** for the network state. ONOS doesn't just push rules once and forget about them; it continuously interrogates the switches every few seconds (usually about every 5 to 10 seconds).

Here is exactly what happens in the background:

1. You use `ovs-ofctl` to manually inject the rule. The switch accepts it.
2. A few seconds later, ONOS polls the switch: _"Give me a list of all your current flow rules."_
3. The switch replies and includes your manual `actions=LOCAL` rule.
4. ONOS checks its internal database and says, _"Wait a minute... I didn't authorize this rule. This is an 'extraneous' alien flow!"_
5. Because ONOS is programmed to aggressively enforce its own state and eliminate unauthorized changes, it immediately sends a delete command (`OFPFC_DELETE`) to the switch to wipe your rule out.

To add manual rules to an SDN network without them being deleted, you cannot go behind the controller's back by talking directly to the switch. You must go _through_ the controller (e.g., using the ONOS REST API or the ONOS Intent Framework) so that ONOS becomes the owner of the rule and protects it!
